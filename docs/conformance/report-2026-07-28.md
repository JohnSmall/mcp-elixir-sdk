# Conformance report — MCP 2026-07-28, official suite

**Written by hand**, like `delta-vs-sprint-4.md` and unlike its other neighbours in this
directory. The censuses and their per-scenario tables are *projections* of `census.json`;
this file is an argument about what those projections mean, and cannot be a projection.
**It derives no figure of its own.** Every number below is quoted from an
adjudicator-**accepted** run. A transcription check re-derives each figure from the
committed artefacts and asserts this file carries it — **the primary statement of each
figure, not every restatement of it**; **§11 names the kinds of figure it covers, the
assertion count for each, and the one thing it does not cover**, and the check asserts that
table against its own tally. The 208-assertion check and its output are on MES-58's
close-out.

**Repo is source of truth; the Confluence page is the mirror.** This file is authored,
reviewed and gated here. The mirror names the commit it mirrors, so that if the two ever
diverge the staleness is *visible* rather than invisible. That is the only mitigation, and
it is stated rather than hidden: two copies exist and the mirror can still go stale.

---

## 1. What this is, and what it is not

* This is a **measurement**, taken with the **official** MCP conformance suite
  `@modelcontextprotocol/conformance@0.2.0-alpha.11`, scored against the **frozen**
  `2026-07-28` requirement set.
* **The suite is a pre-release alpha.** Scenario *membership* is frozen by the requirement
  set; scenario *implementations and check ids are not*, and the alpha line keeps moving.
  A later alpha can turn a scenario red with no change to this SDK's code.
* **Nobody has certified this SDK.** Nothing here is certification by, or endorsement from,
  the MCP conformance project. It is supporting evidence we took ourselves with their
  instrument.
* **The denominator is ADR-003's:** the **core** specification of 2026-07-28, server and
  client, **excluding the authorization profile and the extension track** (Tasks, MCP Apps).
  Out-of-scope scenarios are **named** in §5 and §6, never folded into a rate.
* **Server and client are reported separately, never blended.** They have different
  denominators and different exclusions; one combined percentage would be meaningless.

## 2. The two headline statements

They are **sentences, not numbers**, and each is written to survive being copied out of
this page on its own. Every qualifier a figure needs is inside the sentence that carries it.

### Server

> Against the 37 scored server scenarios of the frozen 2026-07-28 requirement
> set, mcp_elixir_sdk passes 35 under the harness's FAILURE-only rule and 33
> under its stricter rule in which a WARNING also fails. 6 of those 35 are also
> passed by a null server implementing no MCP at all, so 29 is the number of
> scored scenarios whose pass this SDK's own behaviour produced. None of the
> three is a certified conformance rate.

### Client

> Of the 32 scored client scenarios, 25 are `auth/*` — the authorization profile
> ADR-003 puts out of 2.0.0 — leaving 7 in scope. All 7 pass as driven; 5 survive
> both published discounts: drive-policy (removes `request-metadata`) and
> null-passable (removes `http-standard-headers`). Each discount ALONE leaves 6,
> over DIFFERENT sets, so neither 6 may be quoted. The raw figure is 8 of 32 and
> never appears without that exclusion beside it.

**Why 29 is not promoted into a heading.** 29 is *a conservative floor on scenario-level
evidence contributed beyond a minimal valid-envelope null, not a conformance-rate estimate*
(the Sprint 4 claim draft's own words). Written as "29 of 37" in a heading it gets copied
as "78% conformant", which is both wrong and pessimistic in a way that invites a reader to
correct it back to 35 — the outcome the null control exists to prevent. So the sentence is
the headline and 29 is the number it ends on.

## 3. Server leg — three reducers, one control, two real gaps

**There is no single "pass rate".** The harness applies three different rules to the same
run and they do not agree, so each figure names its own rule.

| reducer | scored | rule | scored scenarios failing |
|---|---|---|---|
| `requirements_exit` | **35/37** | FAILURE fails; WARNING is free | `server-stateless`, `input-required-result-non-tool-request` |
| `server_summary` | **35/37** | FAILURE fails; WARNING is free | `server-stateless`, `input-required-result-non-tool-request` |
| `client_summary` | **33/37** | FAILURE **and WARNING** both fail | the two above, plus `sep-2164-resource-not-found` and `input-required-result-ignore-extra-params` |

Check-level census over the scored scenarios: **98 SUCCESS, 19 FAILURE, 2 WARNING,
0 SKIPPED, 0 INFO** (119 checks).

**The denominator is a checked fact, not an assumption.** The frozen set requires 37 scored
and 13 not-scored server scenarios; this run ran all 50. Scored scenarios absent: **none**
(any one refuses the run outright, `SCORED_SCENARIO_ABSENT`). Not-scored absent: **none**.
Ran but outside the frozen set: **none**. Scored scenarios that measured nothing:
**none**.

### The null control, which is what makes 29 sayable

A server answering `-32601` to every method — implementing no MCP behaviour at all — was
run through the same suite. Under `requirements_exit` it scores **6 of 37**. Those 6 are
**named rather than counted**, because a subtracted number a reader cannot audit is not
evidence:

`server-sse-multiple-streams`, `sep-2164-resource-not-found`,
`input-required-result-missing-input-response`,
`input-required-result-unsupported-methods`,
`input-required-result-ignore-extra-params`, `input-required-result-validate-input`.

**What makes the subtraction legal** is coverage: the control ran *every* scored scenario
the measurement ran. Scored scenarios missing from the control: **none** — a census
carrying any is refused (`CONTROL_MISSING_SCENARIOS`) before the table exists. Scenarios
the control ran and the measurement did not: **none**. So 35 − 6 = **29** compares two runs
over one set, not two sets.

### Two scored passes sit over a SHOULD the referee recorded as unmet

`sep-2164-resource-not-found` (3 SUCCESS / 1 WARNING) and
`input-required-result-ignore-extra-params` (1 SUCCESS / 1 WARNING) each pass while
carrying a WARNING raised against this implementation. Both are inside the 35 and outside
the 33. A SHOULD is not a MUST and the claim stands over them — but *which reducer you
read decides it*, so it is said here rather than left inside a number.

## 4. Client leg — the exclusion, the in-scope 7, both discounts, and the inversion

**The raw figure is 8 of 32, and it may not be quoted bare.** 25 of the 32 scored client
scenarios are `auth/*` — the authorization profile ADR-003 puts out of 2.0.0. All three
reducers read 8/32 on this run, and that agreement is a **coincidence of this run, not a
property**: the measurement's 128 checks contain **zero WARNINGs**, and WARNING is the only
status the reducers disagree about.

**The in-scope denominator is 7 scenarios**, named: `http-custom-headers`,
`http-invalid-tool-headers`, `http-standard-headers`, `json-schema-ref-no-deref`,
`request-metadata`, `sep-2322-client-request-state`, `tools_call`.

| figure | value | scenarios removed |
|---|---|---|
| as driven | **7 of 7** | — |
| after drive-policy only | **6 of 7** | `request-metadata` |
| after null-passable only | **6 of 7** | `http-standard-headers` |
| **surviving BOTH** | **5 of 7** | `request-metadata`, `http-standard-headers` |

**The two middle rows are published rather than the endpoints, and that is deliberate.**
They are the same number over **different sets**. Two units independently published
"6 of 7" from those two rows before anyone noticed they were answering different questions.
**Neither 6 may be quoted.** Surviving both: `http-custom-headers`,
`http-invalid-tool-headers`, `json-schema-ref-no-deref`, `sep-2322-client-request-state`,
`tools_call`.

* **Drive-policy** removes `request-metadata`: under a `strict_connect` probe that halts the
  moment `MCP.Client.connect/1` errors — where the measurement adapter logs and carries on —
  the scenario goes red. Its pass depends on our adapter's drive policy, not on a property
  of the SDK. *The reducer choice is load-bearing here*: under the probe `request-metadata`
  scores 7 SUCCESS and 1 WARNING, so `requirements_exit` and `server_summary` would call it
  a PASS and the discount would not fire at all. A derivation reading the wrong reducer
  publishes 6 of 7 with every scenario named, over the right denominator, from two
  adjudicated runs. The discipline produces the difference, not the arithmetic.
* **Null-passable** removes `http-standard-headers`: a null client passes it, so it cannot
  distinguish this SDK from its absence.

### The null control INVERTS on this leg, and it is published as an inversion

| null control | scored | in-scope scenarios it passes |
|---|---|---|
| `2026-07-28-null-connect` | **2/32** | `http-standard-headers` |
| `2026-07-28-null-exit0` | **2/32** | `http-standard-headers` |
| `2026-07-28-null-request` | **1/32** | none |

**A *stricter* null scores *lower*.** The mechanism: for a do-nothing client,
`http-standard-headers` is a pass assembled from eleven SKIPPED checks and not one that
could fail; send anything at all and a twelfth check appears and fails. This is **not**
resolved to whichever null flatters the SDK. The discount is computed under the reading
least flattering to us — *any* null passing a scenario removes it — which is the
`null-connect`/`null-exit0` reading, and it is the reading Sprint 4's figure used.

### `real_gap` is 0 on the client leg, and here is the bound on that

> Outside the authorization profile, this SDK fails **no** client scenario the frozen set
> names — **and** the 24 out-of-scope failures are **measured failures of an absent
> surface**, not empty scenarios: `empty_scenarios` is `[]` in both directions and no
> scored scenario has `SUCCESS + FAILURE == 0`. They cost nothing because of ADR-003, not
> because nothing was measured.

The second half is not a caveat paragraph; it is the rest of the sentence. Publishing the
first half alone would be the flattering read.

One further honesty item: the raw 8 exceeds the in-scope numerator by exactly
`auth/resource-mismatch`, which passes on a **single** SUCCESS check and is passed by every
null control too. It is outside the in-scope denominator on the ADR-003 ground, and it
would be worth nothing inside it.

## 6. Gap register — what Sprint 6 acts on

**The register's own finding, and it is more useful to a planner than the rows:**
**Sprint 6's conformance queue is nearly all ONE existing ticket.** Both real gaps are on
the server leg; five of the six root causes behind them are already owned by **MES-43**;
**12 of `server-stateless`'s 17 failing checks trace to a single missing JSON-RPC-code →
HTTP-status mapping**. And on the client leg:

> **Sprint 6's client conformance queue is empty unless ADR-003 changes.** That is a
> finding, stated in its own sentence rather than left as an absence in a table.

### Gap 1 — `server-stateless` (13 SUCCESS / 17 FAILURE) · severity **high**

It is *the* stateless-core scenario, squarely inside ADR-003's denominator, so none of it is
excused by scope. Decomposed by root cause (R1–R6 as established in
`docs/sprint_4_issues.md`, whose check-level decomposition `delta-vs-sprint-4.md` shows is
unchanged at this run — the 19 scored FAILUREs are `sep-2575` ×17, `sep-2322` ×1,
`wire-schema-valid` ×1 on both sides, zero delta):

| root cause | failing checks | owner |
|---|---|---|
| **R1** `server/discover` does no `_meta` structural validation, so a request with no `_meta`, or missing `protocolVersion`/`clientCapabilities`, gets a normal result instead of `-32602` | `sep-2575-request-meta-invalid-{missing-meta, missing-protocol-version, missing-client-capabilities}` (3) | **MES-43 gap 5** |
| **R2** no JSON-RPC-code → HTTP-status mapping: every dispatch result leaves as HTTP 200 | 12 checks, overlapping R1/R3/R4/R5/R6 | **MES-43 gap 3** |
| **R3** `server/discover` has no version gate, so an unsupported requested version yields a result rather than an `UnsupportedProtocolVersionError` carrying `data.supported`/`data.requested` | `sep-2575-server-unsupported-version-error` (1) | **decision row — see below** |
| **R4** no cross-check of the `MCP-Protocol-Version` **header** against `_meta.protocolVersion` | `sep-2575-http-server-header-mismatch-400` (1) | **UNOWNED — brief drafted, see §8** |
| **R5** a handler error return has no `data` slot, so `-32021` cannot carry `error.data.requiredCapabilities` | `sep-2575-server-rejects-undeclared-capability` (1) | **MES-43 gap 4** |
| **R6** `initialize` is answered `-32022 UnsupportedProtocolVersion`; the scenario requires `-32601` + HTTP 404 for every removed method | `sep-2575-http-server-method-not-found-404-initialize` (also under R2) | **decision row — see below** |

**R3 and R6 are a DECISION row, not a fix row.** Both are documented SDK design decisions
that the referee contradicts — `dispatch.ex:146` names the missing version gate as the
design, and `dispatch.ex:66-68`/`:131-139` document `initialize → -32022` and why. PM ruling
(MES-24, comment 24503) routes them to the **release ticket as decisions requiring a PO
call**, *not* to MES-43 as gaps to fix. They are carried here so the measurement is not
lost and so **nobody schedules them as bugs**.

**Two corrections to how this scenario has been described, both verified against the run's
own saved check sheet** (`server-server-stateless-2026-08-21T03-55-01-582Z/checks.json` in
the accepted run directory):

* The census's `classification.why` for this scenario describes sub-cause (d) as
  *"`error.data.requiredCapabilities` is an array where the schema defines an object of
  capability objects"*. **The observed response carries no `error.data` at all** — the
  value is stringified into the error *message*
  (`"Missing required client capability: sampling (requiredCapabilities: {\"sampling\":{}})"`).
  The harness's message mentions an array only because its generic wording explains the
  schema; it did not observe one. **R5 is the correct mechanism, and MES-43 gap 4 is the
  correct owner** — a fixer told to change an array's shape would be looking for something
  that does not exist. Recorded as **S5-29**.
* The same prose enumerates **four** sub-causes accounting for **16** of the 17 failing
  checks. The seventeenth — `sep-2575-http-server-header-mismatch-400` — appears in none of
  them. It is R4's check, and R4 is the one root cause with no owning ticket. Recorded as
  **S5-30**.

### Gap 2 — `input-required-result-non-tool-request` (0 SUCCESS / 2 FAILURE) · severity **high**

MRTR is wired to `tools/call` alone (**MES-43 gap 1**), and `Dispatch.complete/1` overwrites
a handler-supplied `resultType` unconditionally (**MES-43 gap 8**). SEP-2322 makes
`InputRequiredResult` **universal**; the scenario is, in MES-43's own words, *structurally
unpassable* — no conformance handler anyone could write passes it. Severity is high because
the conformance claim currently implies we are universal.

Stated above as a finding rather than left as an empty table.

### The one contradiction, stated in full

The draft says the claim rests on **"our own ported acceptance suite"**. That sentence was
written to ADR-003's Consequences bullet, which is **conditional**:

> *If the conformance harness still lacks stateless-core scenarios (it had none at the
> Sprint 3 measurement), the claim rests on our own ported acceptance evidence, and says so
> rather than implying harness certification.*

**The condition's antecedent is false and has been since before Sprint 4 measured.**
`@0.2.0-alpha.11` carries a full 2026-07-28 suite — 37 scored server scenarios and 32
scored client scenarios — and Sprint 4 used it. So the justification **lapsed without the
sentence changing**, which means it still reads as considered. That is exactly the class
recorded as **S5-24**: *a guard's stated justification can lapse without the guard changing,
and a lapsed justification reads as considered.*

**This report states and routes it; it does not rewrite the claim.** The claim wording is
owned by the release ticket under ADR-003 sub-decision 6, where the PO owes the final
wording. What the release ticket needs to know is that the sentence is now false in a
direction that **understates** our evidence, and that the honest replacement is roughly
*"measured with the official suite, pre-release alpha, with adjudicated provenance; not
certified by anyone"*.

## 8. New finding — a root cause with no owning ticket (brief for the PM)

**R4 is unowned.** Established rather than assumed:

* `docs/sprint_4_issues.md` names R4 as a root cause of `server-stateless`: *no cross-check
  of the `MCP-Protocol-Version` header against `_meta.protocolVersion`;
  `check_routing_headers/2` covers `Mcp-Method`/`Mcp-Name` only.*
* The MES-43 escalation list (`sprint_4_issues.md`, "Escalations this leg produced") routes
  gaps 1–5, 7 and 8; **R4 is in none of them**. MES-43's ticket body is SEP-2322/MRTR and
  does not mention it. MES-45 covers *trailing OWS on `Mcp-Name`/`Mcp-Method`* and
  *`Mcp-Param-*`/`x-mcp-header` validation* — different headers, different checks. A sweep
  of every open MES ticket description for `protocol-version` / `header-mismatch` / `-32020`
  finds no owner.
* **MES-43's gap 3 does NOT close it incidentally**, which was the reason to check rather
  than assume. The harness sends `_meta.protocolVersion = "v999.0.0"` with
  `MCP-Protocol-Version: 2026-07-28` and requires **HTTP 400 *and* JSON-RPC `-32020`**. The
  observed result is *"got status 200 with code undefined"* — **no error was produced at
  all**. Status mapping (gap 3) can only map an error that exists; the mismatch must first
  be **detected**. So R4 is independently necessary.

**Proposed Sprint 6 ticket** — *the server does not cross-check the `MCP-Protocol-Version`
header against `_meta.protocolVersion`, so a mismatched request is served normally.*
Scope: detect the disagreement on the request path and answer `-32020` HeaderMismatch;
the HTTP-400 half arrives with MES-43 gap 3 and the two must land together for the check to
pass. Sibling of MES-45 in shape (routing-header handling) but a different header and a
different requirement, so it is a candidate to **join MES-45** rather than be raised
standalone — a call for the PM. Severity: moderate — one scored check, inside the
stateless-core scenario, and a documented MUST.

*Raised as a brief only. CODE_CREATOR does not raise tickets.*

## 10. Bounds — what this report does not establish

1. **Not certification.** Pre-release alpha, run by us, on our own adapters.
2. **Adapter fidelity is not established.** Acceptance ties a figure to a tree; it does not
   show the adapter faithfully exercises the SDK. A conformance adapter can flatter its
   subject, and only the null controls bound that — which is why the controls are published
   beside every figure.
3. **The instrument moves.** `checkMcpNameHeader` is dormant today only because every
   alpha.11 fixture name happens to be header-safe; one non-safe fixture name in a later
   alpha turns this SDK's spec-correct encoding red with no code change.
4. **Not-scored is not "passed".** 13 server and 7 client scenarios run and are reported and
   never counted, in either direction.
5. **Five of the seven Known limits are unmeasured by this suite** (§7). A green run is not
   evidence against any of them.
6. **The historical side of any comparison cannot be adjudicated.** No run of a tree
   predating the adjudicator can ever be accepted (S5-14), so Sprint 4's figures are quoted
   as a *claim under review*, never as a second adjudicated number.

## 11. How every figure above is checked, and exactly what that does not cover

Every figure above is a hand-copy, so a script re-derives each one from the **committed**
artefacts and asserts this file carries that value. It proves **transcription, not
correctness**: the censuses are the authority, and this only establishes that the report
agrees with them.

**Two bounds travel with that guarantee, because "every number is checked" would promise
more than it delivers.** First, it binds the **primary statement** of each figure — the
sentence, table row or cell where the report states it — and not every later restatement of
the same number; a figure quoted again in passing is not separately asserted. Second, some
assertions are **artefact-side**: they assert a property of a committed artefact rather than
a needle in this file, so they are part of the check without being report coverage. They get
their own column below instead of being folded into one number that overstates the cover.

**The kinds of figure are closed by this report's own structure**, so every §-numbered
section that carries a figure has a row here. A section with figures and no row would be
uncovered *and* unadmitted, which is the defect this table exists to prevent.

Beside the figures, **5** forbidden-shape assertions cover shapes this report must *not*
have — a bare rate in a heading, a tier claim, a bare-percentage conformance claim, a claim
of certification — and **18** more assert this very table against the script's own tally: one
per row, one for the forbidden-shape count, one for this sentence's own count, and one for
the total. **208 assertions in total**.

**The §2 row exists because it once did not.** The headline sentences are the ones most
likely to be copied out alone, so they are what a transcription guarantee most needs to
cover; at `cdb19e4` they were the one thing it did not cover, and changing `5 survive` to
`6 survive` in the client headline left the check green. They are now asserted against the
blockquote text **itself** rather than against the report as a whole, so a needle satisfied
by some other paragraph cannot stand in for them.

**The §6 and §8 rows exist for the same reason, one round later.** §6's root-cause row was
published as a zero, on the stated ground that no committed artefact carried the check-name
sheet. That was wrong about a committed artefact: `server-2026-07-28.json` carries
`failed_checks`, every failing check id for `server-stateless` **by name**. So the names and
the counts are asserted — each name in the R1–R6 table is parsed out of *this file* and
looked up in that list, each parenthetical is asserted against the number of names beside
it, and R2's `12` is asserted against the failing checks whose own message states an HTTP
status. §8 had no row at all while the table was published as complete.

**What is not checked, and it is one thing: the attribution.** *Which* root cause a given
failing check belongs to is a reading of the run directory, which is **not committed** — only
the censuses are — so no assertion here could be made to fail on a wrong grouping. S5-30's
**16** is a figure of that same kind: it counts how many failing checks the census's
`classification.why` prose accounts for, which is a property of the grouping and not of the
census's numbers. **A Sprint 6 planner should treat the grouping as an argument to verify
against the run, and the names and counts as transcribed.**

**One more bound, on the check that guards the mirror.** The Confluence payload is compared
to this file token by token, so a rendering that drops, reorders or invents a sentence fails.
It proves the two copies **agree**; a figure wrong in *both* passes it. It is a divergence
check, not a second opinion, and the transcription check above is what makes the shared value
right in the first place.
