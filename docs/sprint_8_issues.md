# Sprint 8 — procedure defects

Procedure defects found while working Sprint 8 (epic MES-65): things wrong with
**how we work** — the gate set, the briefs, the tooling contract.

Ticket substance does not go here. Findings about the MCP SDK itself, about
conformance results, or about a specific ticket's deliverable belong in comments
on that ticket. This file is for defects a *future* sprint would otherwise hit
again.

Each entry states the **mechanism**, because the mechanism is the transferable
part.

---

## S8-1 — A regenerated artefact moved a figure the prose states in five places, and nobody restated the prose. Third instance of the same shape.

**Found:** MES-87, 2026-09-09, by CODE_CREATOR, while grounding the blast radii for
the criterion amendment. **Fixed here**, on the PM's Q1 ruling (`26736`).

**The defect.** `docs/conformance/etcc-register.md` stated the out-of-scope population
as **413** in five places (`:197`, `:214`, `:425`, `:1411`, `:1414`). The delivered
`docs/conformance/etcc-register.json` said **428**.

**The mechanism, and it is the transferable part.** The figure is not a *claim* in the
prose — it is a **transcription of a derived artefact's field**. The artefact is
regenerated by a script; the prose is not. So the two drift the moment anything
upstream of the script changes, and nothing in the toolchain notices:

    85d50fa   etcc-register.json  totals.out_of_scope = 413    artefact rows =  992
    18df3a6   etcc-register.json  totals.out_of_scope = 428     artefact rows = 1007

MES-84 (`18df3a6`) regenerated `etcc-exunit-rows.json`, `test/conformance/` had grown by
**15** units, `out_of_scope` moved 413 → 428, and the prose was not restated. **No label
moved and the in-scope 579 is untouched** — 579 + 428 = 1007 — so nothing was *wrong*,
only stale.

**Why it matters more than a stale number usually would.** This is precisely
*"regenerated without restating the totals"*, which is the failure mode MES-87's own
**AC4** exists to prevent, and it is the **third** instance of that shape in this epic
after **F10** and **F12**. A rule the process states as an acceptance criterion was
being broken in the document the criterion was written about.

**What would actually stop it recurring, and it is not "remember to restate".** Every one
of these five figures is mechanically derivable from the committed JSON. The generator
already refuses to write a register whose labels do not sum (§7); the same discipline
applied to the *prose* would be a control script asserting that each figure the document
states matches the artefact field it transcribes. That is a proposal, not a decision — it
belongs to whoever owns the form-and-totality checker `§B.1.3` records as **having no
owner**.

**One detail worth copying.** The `:425` occurrence is a transcript of
`mix run conformance/controls/etcc_register_controls.exs totality`. It was **re-run**
and the real output pasted, not hand-edited to 428. Hand-editing a transcript makes it
agree with the artefact while destroying the only evidence that the script agrees too.

## S8-2 — Stale line citations that land on a DIFFERENT REAL TEST, in a document whose own JSON is correct

**Found:** MES-87, 2026-09-09, by CODE_CREATOR, while re-deriving §6.1's caller
enumeration from the AST instead of inheriting it. **Recorded, NOT fixed** — raised for
the PM to scope.

**The defect.** `docs/conformance/etcc-register.md` §6 and §7 cite rows in
`test/mcp/client_test.exs` by bare line number — §7 family C's three ruling-C rows as
`:353`, `:359`, `:425`, its 17 call sites as `143, 166, 184, …`, and §6's six worked
cases as `:141`, `:182`, `:124`, `:89`, `:347`, `:353`. **Most no longer resolve.**
MES-84 (`18df3a6`) inserted `@tag :etcc` lines into that file, shifting declarations
progressively by up to +18.

**The mechanism, and it is worse than ordinary drift.** A stale citation has three
possible landing sites, and they are not equally visible:

| lands on | example | how it reads |
| --- | --- | --- |
| a blank line | `:353`, `:141`, `:124`, `:347` | obviously broken — **safe** |
| nothing (past EOF) | — | obviously broken — **safe** |
| **a different real test** | `:359` now reads `test "close is idempotent"`, which §6 cites as `:347` | **plausible, and therefore silently wrong** |

The third case is the dangerous one. A reader checking `:359` finds a real test with a
real name and no reason to doubt it. And the shift is **not uniform** — `:89`
(`"starts ready by default"`) still resolves correctly, because the inserted lines are
below it — so spot-checking one citation and finding it good licenses nothing.

**The data is fine; only the prose is stale.** `etcc-register.json`'s `evidence` fields
carry the **current** call sites (`146, 170, 189, …`), which is exactly what an AST
re-derivation at this tip reproduces. So this is **prose-vs-data drift** — the same
shape as S8-1, one document along, and the second instance in one ticket.

**Why it was not fixed here.** It is dozens of citations across MES-81's document, which
MES-87 amends at one figure only (S8-1). Absorbing a wholesale citation re-resolution
into a criterion-amendment ticket is the scope growth the seat model exists to prevent.

**The transferable rule.** *A line-number citation into a file that other tickets edit is
a citation with an expiry date, and it expires silently.* Where a stable key exists —
`etcc-register.json` keys rows on `{module, test name}` precisely so that it does not
have this problem (`etcc-row-key.md` §1) — **prose should cite the key, not the line.**
The register's own JSON already got this right; its prose did not.

## S8-3 — A one-hit scan and a broken scan are indistinguishable from the hit count

**Found:** MES-87, 2026-09-09, by CODE_CREATOR, enumerating §6.1's asserting helpers.
No defect was present — this records the method that established that.

**The situation.** §6.1's population is *"every unit whose ONLY gate-2-and-3-passing
assertion is inherited from a helper"*. The sweep for asserting helpers across all 39
files of `test/mcp/` returned **one**: `defp do_connect/2` at `client_test.exs:59`.

**One hit is exactly the result a broken sweep produces.** A regex that mis-anchors, an
AST walk that never descends, a wildcard that matches nothing — all return a small
number confidently. The first attempt here *was* a line-oriented `awk`, and it returned
**eight** hits, of which seven were artefacts of a one-line `defp` swallowing the blocks
below it. Believing either number without a control is the defect.

**The two controls that settled it, and they do different jobs:**

1. **A positive control — print what the scan SEES, not only what it selects.**
   *39 files walked, 137 `def`/`defp` reached, 10 `setup`/`setup_all` reached.* This
   rules out "walked nothing". It does **not** rule out "walked everything and cannot
   recognise an assertion".
2. **A mutation — inject the thing being looked for and require the count to move.**
   `assert 1 == 1` into `state_handle_test.exs:6`'s `setup` moved the setup count
   `0 → 1` and named the block. This is what proves the predicate LIVE. Reverted, tree
   re-verified clean.

**The rule.** *A positive control proves the sweep reached the population; only a mutation
proves the predicate can fire.* Neither substitutes for the other, and a zero or a one is
the result that most needs both. The same pairing was used on guard 22 — five mutations,
each fired on its own distinguishing clause, plus an unmutated positive control that
builds — because a guard that has never been seen to go red is a guard nobody has tested.

## S8-4 — "Adopt" and "reject" are not symmetric when the register already applies the ruling

**Found:** MES-87, 2026-09-09, by CODE_CREATOR, at the plan hop. Not a defect; a
transferable framing that changed how the ticket was planned and reviewed.

**The observation.** MES-87 promoted three §9 tie-breaks into ratified criterion. The
delivered register **already applied all of them**, through MES-81's rounds 2–6.
Therefore:

- **ADOPTING** a candidate moves **0** rows. It changes where the rule *lives*, not what
  the data says.
- **REJECTING** one is what moves rows — candidate 1's rejection would have put **66**
  rows back in play, `ET-CC` 281 → up to 347, a **23%** move.

**Why this is worth recording rather than obvious.** A ticket whose acceptance criteria
say *"quantify every rows-affecting change before ratifying"* reads as though the risk is
in the adoptions. It is in the **rejections**, and a plan that prices only what it intends
to do prices the wrong branch. The right shape is: **price the branch you are not taking**,
because that is the number the reader cannot derive from the delivered artefact.

**The corollary that keeps the zero honest.** If adopting moves 0 rows by construction,
then a measured 0 proves nothing on its own — it is also what a generator that ignores
its inputs produces. **The no-op control comes first**: regenerate with nothing changed
and require byte-identical output. Only then does the later zero-diff carry information.
