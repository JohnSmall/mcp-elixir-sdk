## 3. How the work runs

The binding procedure is Confluence **250052681** and the repo's `CLAUDE.md` plus
`docs/procedure/`. In short: three seats (PM, CODE_CREATOR, CODE_REVIEWER), one ticket in
flight, flow **PM→CC→PM→CR→PM**, the Jira assignee is the baton, the brief is the ticket
body, everything else is ticket comments. The PM squash-merges as `Project-Manager`, bumps
`mix.exs` line 4 (D4, `2.0.0-dev.N`), tags `2.0.0-dev.N — [KEY] title`, pushes `main` and the
tag and runs `mix origin.sync`.

Standing rules the PO set, carried as given:

- Don't work around acm. Report acm problems on ACM-38 or the relevant ACM ticket.
- Per-ticket worktrees are mandatory. At merge: `git worktree remove` (no `--force`), then `git branch -D`.
- Run tickets strictly one at a time, PM→CC→PM→CR→PM.
- A DoD gate change is a Task (not a PM Task).
- Confluence changes go through the PM.
- Check environment variables by name only; never print a credential value.
- Any extra process started for evidence starts from `env -i` with decoy credentials only.
- Gate 5 is 22 seeds (0 and 1000001–1000021), run strictly serially and alone.
- Never edit `/workspace/acm-seats`.
- Process checks use pid and comm only; never read another process's argv or environ.
- The CR seat engine is codex.
- A red seed is recorded red and never re-run to green. CR's run is binding. A gate-7
  exception is the PO's call only. PO questions go in yes/no form.
